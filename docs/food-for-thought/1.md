The agentic orchestration relies on **LangGraph** as the central nervous system, managing a stateful flow of operations. This isn't a linear "chain"; it's a cyclical graph where the agent perceives, reasons, and acts.

### **The Orchestration Flow**

1.  **State Initialization:**
    Every interaction starts with a `TutorState` object. This holds the conversation history, the user ID, and crucially, the *current pedagogical context* (e.g., "The user is stuck on Algebra basics").

2.  **Node 1: Knowledge Retrieval (The "Librarian")**
    * **Input:** `TutorState`
    * **Action:** The agent queries **Neo4j** to understand where the current concept sits in the curriculum.
    * **Logic:** "If the user is asking about 'Quadratic Equations', what are the prerequisites? Does the user have mastery in 'Factoring'?"
    * **Output:** Updates `TutorState` with a list of prerequisites and the user's mastery status from Supabase.

3.  **Node 2: Reasoning Engine (The "Pedagogue")**
    * **Input:** `TutorState` (now enriched with knowledge graph data).
    * **Action:** This is the core "agentic" step. It uses a **LearnLM-tuned model** (via Gemini) to decide *what to do next*.
    * **Mechanism:** It produces a **structured output** (enforced by Pydantic) that classifies the user's intent and selects a strategy.
    * **Strategies:**
        * *Scaffold:* The user is struggling; provide a hint, not the answer.
        * *Explain:* The user is asking a conceptual question; provide a Socratic explanation.
        * *Quiz:* The user claims to understand; verify with a question.
        * *Redirect:* The user is off-topic; gently bring them back.
    * **Output:** Updates `TutorState` with a `PedagogicalDecision` object.

4.  **Node 3: Responder (The "Voice")**
    * **Input:** `TutorState` (containing the decision).
    * **Action:** Generates the actual text response to the user.
    * **Logic:** It takes the decision (e.g., "Scaffold") and retrieves specific content from **ChromaDB** (e.g., a textbook definition or example) to ground the response. It then uses a **Few-Shot Prompt** (dynamically selected based on the strategy) to ensure the tone is supportive and Socratic.
    * **Output:** A JSON object containing the text response and suggested follow-up actions (validated by Zod on the frontend).

5.  **State Persistence & Loop**
    * **Action:** The final state is saved to **Redis**.
    * **Logic:** If the `next_action` implies a multi-turn interaction (e.g., a quiz), the graph waits for user input. If the action was "Update Mastery," a background process updates **Supabase**.



### **Visualizing the Graph**

Imagine a flow chart where:
* **Start** $\rightarrow$ **Retrieve Knowledge (Neo4j)**
* **Retrieve Knowledge** $\rightarrow$ **Reasoning Engine (Gemini + Pydantic)**
* **Reasoning Engine** $\rightarrow$ **Responder (ChromaDB + LearnLM)**
* **Responder** $\rightarrow$ **End** (Wait for user)

This architecture ensures that every response is:
1.  **Context-Aware:** Knows *where* in the curriculum the student is.
2.  **Pedagogically Sound:** Follows LearnLM principles (scaffolding, Socratic questioning).
3.  **Grounded:** Uses actual educational content, not hallucinations.
4.  **Structured:** Returns reliable data types for the UI.
